### Unauthenticated /admin action: full founders-admin mutation surface open to anyone who knows an allowlisted shop domain

- **File:** `app/routes/admin.tsx`:484
- **Lane:** security-sweep

The founders admin LOADER requires authenticate.admin, but the ACTION deliberately skips it. A POST to /admin?shop=hx5hqt-na.myshopify.com from anywhere on the internet (no cookie, no session token, no HMAC) passes the gate as long as that shop string is in ALLOWED_SHOPS and has any row in the Prisma session table. The two allowlisted domains are static strings; once known (repo, logs, social engineering, or simply because the founders' store is public), an attacker can: rewrite transformation prompts for any product/variant (update-prompt/update-variant-prompt, arbitrary prompt injection into every customer's AI transform), change AI model per product (cost escalation to Pro), upload/remove reference images for any product UUID, toggle is_skin_analysis_enabled and vto_enabled for ANY shop domain (targetShopDomain is attacker-supplied and not restricted to the allowlist), and trigger session refreshes. This is cross-tenant write access to live merchant data with zero authentication.

**Evidence:** action reads `const shopParam = url.searchParams.get("shop")`, then `prisma.session.findFirst({ where: { shop: shopParam }})` and `if (!shopDomain || !ALLOWED_SHOPS.includes(shopDomain)) return 403` (admin.tsx:490-504). No authenticate.admin, no token verification — the comment admits it: "Skip authenticate.admin for the action... The loader already verified Shopify auth" (admin.tsx:485-489), but Remix actions are independent HTTP requests; nothing links the POST to a verified loader session. update-skin-analysis-enabled / update-vto-enabled then update shops by attacker-supplied `targetShopDomain` (admin.tsx:726-776).

**Verifier:** Confirmed by reading /Users/charles/glimpse-app/app/routes/admin.tsx. The action (line 484) performs no authentication: it reads `?shop=` from the URL, checks a Prisma session row exists for that shop, and checks the string against the hardcoded ALLOWED_SHOPS array (lines 49-52). No authenticate.admin, no session token, no HMAC, no cookie — the comment at 485-489 explicitly documents the skip. /admin is a top-level flat route outside the authenticated /app layout, and no middleware or other guard exists. The allowlisted myshopify domains are static strings that are effectively public (exposed on any Shopify storefront as Shopify.shop), and both shops will always have session rows since the app is installed there. Impact verified in code: update-prompt/update-variant-prompt write transformation prompts by bare UUID with no shop scoping (prompt injection into customer-facing AI transforms), update-ai-model forces expensive models, reference-image mutations are open, and update-skin-analysis-enabled/update-vto-enabled (lines 726-776) update the shops table by attacker-supplied targetShopDomain with no allowlist restriction — cross-tenant writes to ANY merchant. refresh-sessions triggers Shopify API calls with stored offline access tokens. This is an unauthenticated, internet-reachable mutation surface over live multi-tenant data; the only barrier is knowledge of a static domain string, which is not authentication. Severity critical stands.

**Fix sketch:** Have the founders-admin fetchers send the App Bridge session token (Authorization: Bearer) with POSTs and call authenticate.admin(request) in the action — session-token auth on XHR does not trigger the redirect bounce that motivated the skip; then verify session.shop is in ALLOWED_SHOPS before any mutation, and drop the query-param shop lookup entirely.

**Verifier:** Confirmed by reading the code. - **File:** `app/lib/supabase.server.ts`:2513
- **Lane:** onboarding-journey

ensureShopExists caches shop existence in a process-level Set with the comment 'Existence is permanent — once seen, skip the round trip'. But existence is NOT permanent: webhooks.app.uninstalled.tsx calls deleteShopData(shop), which deletes the shops row (Step 7, ~line 1506-1523). If the same merchant reinstalls while the same server process is alive (Render is long-lived; trial merchants uninstall/reinstall constantly), ensureShopExists returns early and never recreates the row. Every downstream path then breaks: (a) updateOnboardingStep/saveOnboardingSurvey/completeOnboarding call ensureShopExists (no-op) then UPDATE shops matching 0 rows — succeeds silently (the exact known past bug pattern #2), so the wizard restarts at step 1 on every reload and survey data is lost; (b) /app/api/catalog-sync and /app/api/quiz-generate return 404 'Shop not found' (findShopByDomain null), so onboarding step 4 sync errors out; (c) the /studio loader throws 404 'Shop not found' (studio.tsx:97), so 'Open Quiz Studio' shows an error boundary inside the modal. The reinstalled merchant is hard-stuck until the next deploy/restart. No afterAuth hook exists in shopify.server.ts to recreate the row either.

**Evidence:** supabase.server.ts:2510-2513: `if (knownShopDomains.has(shopDomain)) return;` with no invalidation anywhere (grep shows knownShopDomains only referenced inside ensureShopExists). webhooks.app.uninstalled.tsx:23 calls deleteShopData(shop); deleteShopData Step 7 (`.from('shops').delete().eq('id', shopId)`) removes the row. updateOnboardingStep (supabase.server.ts:2542-2555) does UPDATE with only console.error on error and no 0-row check. studio.tsx:96-97: `if (!shop) throw new Response("Shop not found", { status: 404 })`. app.api.catalog-sync.ts:35: `if (!shop) return json({ ok: false, error: "Shop not found" }, { status: 404 })`.

**Verifier:** Every evidence line checks out. knownShopDomains (supabase.server.ts:2508) is only referenced inside ensureShopExists — no invalidation exists anywhere. webhooks.app.uninstalled.tsx:23 calls deleteShopData, whose Step 7 (supabase.server.ts:1507-1510) deletes the shops row without touching the cache; the webhook runs in the same Remix process that holds the cache. shopify.server.ts has no afterAuth hook, and the only other shops-row creation path is saveProductConfiguration in the legacy /app/products flow, which quiz-first onboarding merchants never reach (app.tsx:25-28 comment confirms ensureShopExists is the sole creation path for them). Downstream: updateOnboardingStep/saveOnboardingSurvey do UPDATEs with only console.error and no 0-row check (silent no-op, the project's known silent-write pattern), getOnboardingState falls back to step 0 so the wizard restarts every reload, studio.tsx:97 throws 404, and app.api.catalog-sync.ts:35 returns 404. ### Quiz cart-token validator rejects modern Shopify cart tokens ("?key=" suffix) — quiz conversion attribution silently dead

- **File:** `extensions/glimpse-widget/assets/gleame-quiz.js`:262
- **Lane:** storefront-quiz-journey

The quiz's acceptToken() requires the whole token to match /^[a-zA-Z0-9-_]+$/ and be <= 64 chars. Current Shopify cart tokens returned by Liquid cart.token and /cart.js carry a "?key=<hex>" suffix (contains '?' and '=', and typically exceeds 64 chars), so acceptToken returns null for every modern token. cartToken therefore stays null, quiz_add_to_cart (and all other quiz events) are sent WITHOUT a cartToken, and the orders/create webhook (which joins on order.cart_token) can never link a purchase to the quiz. Merchants see quiz activity but zero attributed conversions — the app's headline ROI metric — with no error anywhere. The sibling widget was explicitly fixed for exactly this (billing review, 'money paths hardened') but the quiz was missed.

**Evidence:** gleame-quiz.js:262-266: `if (!/^[a-zA-Z0-9-_]+$/.test(t) || t.length > 64) return null; if (/^[0-9a-f]{32}$/.test(t)) return null;` — no '?' stripping. Contrast widget.js:187-191, deliberately hardened: `const stripped = String(t).split('?')[0]; return (stripped && !isLegacyHex(stripped)) ? stripped : null;` with the comment that legacy tokens are un-joinable and orders/create never echoes them. refreshCartToken() (gleame-quiz.js:268-278) feeds /cart.js tokens through the same broken validator before trackEvent('quiz_add_to_cart') at line 2170. webhooks.orders.tsx joins on order.cart_token (line 21, 174).

**Verifier:** Confirmed by direct code reading. gleame-quiz.js:261-266 acceptToken requires the full token to match /^[a-zA-Z0-9-_]+$/ and length <= 64; the '?key=<hex>' suffix on modern tokens contains '?' and '=' and fails this, returning null. The codebase's own comment at app/lib/supabase.server.ts:310-315 states that Liquid cart.token and /cart.js return the keyed form while orders/create delivers the bare id, which is exactly why normalizeCartToken and the widget.js fix (widget.js:186-192, split('?')[0] plus /cart/update.js force-mint fallback) exist. The quiz received neither the strip nor the fallback, so cartToken stays null for both sources (data-cart-token at line 267 and refreshCartToken at 268-278), quiz_add_to_cart (line 2170 -> trackEvent line 290) is sent without cartToken, and the analytics_events-to-widget_orders join on cart_token can never match a quiz event. No guard elsewhere compensates: the server-side sanitizer in api.storefront.track-event.ts:132-139 uses the same restrictive regex and only sees what the client sends. Failure is completely silent. Severity high is appropriate (headline conversion-attribution metric silently zero for the quiz on all modern stores), but not critical since no security, data-corruption, or direct billing impact.

**Fix sketch:** In gleame-quiz.js acceptToken, mirror widget.js: strip the query suffix first (const stripped = String(t).split('?')[0]) then reject only legacy 32-hex tokens; optionally also add the /cart/update.js force-mint fallback used by widget.js so sessions without a cart still get a joinable token.

## Refuted findings

- **Vanished-variant sweep soft-deletes legacy numeric-id variant rows (and duplicates them) the moment sync is enabled on a pre-pivot shop — recommendation engine then drops them** (onboarding-journey): The code mechanics are accurately described: catalog-sync.server.ts normalizes legacy numeric ids for products only (lines 231-264), the variant upsert keys on GID (296-311), the sweep soft-deletes rows absent from the incoming GID set (320-348), and recommendation-engine.server.ts:128 filters status==='deleted'. However, the failure requires a variant row storing a bare numeric shopify_variant_id, and the finder's only evidence such rows exist is the runtime fallback at supabase.server.ts:1106-1119. Git history refutes that inference: the fallback shipped in commit d7560f2, the same commit that introduced variant support, with 'Handles both GID and numeric IDs' as a day-one defensive feature (the widget sends numeric Liquid variant ids) - it predates any production variant rows and proves nothing about stored formats. Every writer of shopify_variant_id in repo history stores GraphQL GIDs: app.products.tsx used admin.graphql from its first version (47ab6d3), the L&M backfill scripts write GraphQL v.id, catalog-sync writes GIDs, and admin.tsx only updates by row UUID. Migration 001 documents the column as GID with GID test data. The specifically named at-risk shops are demonstrably unexposed: the ORLY backup snapshot contains zero variant configs and all-GID product ids, and L&M variants come from GID-writing backfills. The product/variant normalization asymmetry is principled, not an oversight: products.shopify_id has a real numeric-legacy history; product_variants never did. With no code path ever having written numeric variant ids and no evidence of out-of-band rows, the corruption scenario is not conclusively reachable. At most this is a cheap symmetry-hardening opportunity, not a high-severity live-data corruption bug.

- **Per-shop save lock is in-process only — rolling deploys or a second instance void serialization on the wipe-and-rewrite save path** (concurrency-sweep): The code facts are accurate: withShopSaveLock (app/lib/shop-save-lock.server.ts:13) is an in-process promise-chain Map, the save_recommendation_config RPC (latest in supabase-migrations/055_question_max_selections.sql) is wipe-and-rewrite with no pg_advisory lock, FOR UPDATE, or version check anywhere in supabase-migrations/, and all live-write paths rely solely on this lock. However, the claimed failure requires two concurrently-serving processes, and the current deployment is a single Render FREE-tier web service (docs/quiz-setup.md:21-25 explicitly notes free-tier spin-down). Render free instance types do not perform zero-downtime deploys - the old instance stops before the new one serves - so there is no old/new overlap window, and free tier cannot scale out, so no second instance exists. The finder's overlap mechanism only applies to paid instance types. The limitation is also explicitly documented in the file's own header as a deliberate design decision with a stated remediation for when the single-instance assumption changes. A documented constraint whose triggering precondition (multi-process operation) does not exist in the deployed environment is not a currently reachable bug. It would become real only after an infra upgrade, at which point adding pg_advisory_xact_lock in the RPC is the intended fix.
